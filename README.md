## 它做什么

```
Paper 后端 × N                        Velocity 代理
┌──────────────┐                     ┌──────────────────┐
│ PerfScope    │  plugin messaging   │ PerfScope-       │
│ + network    │ ──────────────────► │ Velocity         │
│   .enabled   │  perfscope:summary  │ /pscope network  │
└──────────────┘                     └──────────────────┘
```

后端只发一份**极小的摘要**（TPS / MSPT / 玩家数 / 采集是否还活着），代理侧负责聚合与显示。

## 一条必须知道的限制

**plugin messaging 必须搭玩家的连接转发，所以空服的后端不会上报。**

这不是实现缺陷，是这条链路本身的固有限制。它直接决定了面板该长什么样：空服的后端必须显示成
「无数据」，**不能**显示成「正常」或「TPS 0」。把这三件事混成一个「-」，是仪表盘最常见的谎言——
服主看到「-」会以为没问题，看到「0」会以为服务器挂了，而真相往往只是没人玩所以没有转发通道。

## 权限

命令 `/pscope network`（别名 `/perfscope network`、`/ps network`），权限节点 `perfscope.network`。

> ⚠️ **别名会盖住后端的同名命令。** Velocity 上代理命令优先于后端命令，而本插件注册了
> `perfscope` 作为别名，所以玩家在游戏里敲 `/perfscope tps` 会被这里接住、只回一句
> 「用法：/pscope network」，后端 24 个子命令全部不可达。要用后端命令请**走控制台**，
> 或写成带插件命名空间的 `/perfscope:perfscope tps`。

> **为什么不是 `/perfscope:tps`**（已在 Paper 1.21.4 实机验证）：Bukkit 的 `knownCommands` 键是
> `<插件名>:<命令名>`——插件名取自 `plugin.yml` 的 `name`（`PerfScope`），命令名取自
> `Command.getName()`（`perfscope` / `pscope` / `perf`）。`tps` 是**子命令**，从不进命令表，
> 所以 `/perfscope:tps` 会返回 `Unknown or incomplete command`；
> `/perfscope:perfscope tps` 与 `/perfscope:pscope tps` 才会命中后端子命令。

**默认谁都看不到，包括玩家。** Velocity 没有 `plugin.yml` 那种权限声明，插件无法给节点设默认值；
没装权限插件时 Velocity 的 `permissionFunction` 是 `ALWAYS_UNDEFINED`，`hasPermission` 返回 `false`。
这是保守的正确默认，但你需要知道它——**装完发现玩家用不了，通常就是这个原因**。

授权步骤：装一个权限插件（LuckPerms 等）→ 给玩家或组加 `perfscope.network`。

**失败形态容易误判**：没权限时 Velocity 会把命令**转发到后端**执行，玩家看到的是
**后端 PerfScope 的帮助页**，不是"你没有权限"。看到帮助页而命令没反应时，先查权限。

**授权前请确认面板会展示什么**：所有后端名（含从未上报的）、各自 TPS / MSPT / 在线人数、
全网在线合计。如果后端名里带了内网主机名之类信息，它会原样出现在这个玩家的聊天窗口里
（后端名按显示宽度截到 20 格，超出部分用 `…` 标出，但**不会被隐藏**）。

**控制台始终可用**（按类型白名单放行，不是"任何非玩家都放行"）。

## 五种状态

面板上每一行必定是这五种之一，且它们的含义完全不同：

| 状态 | 含义 | 该去查什么 |
|---|---|---|
| `正常` | 有新鲜数据，采集器活着 | 无需处理 |
| `数据过期` | 收到过，但超过 3 × 该后端上报间隔没更新 | 可能刚空服，也可能后端没响应 |
| `采集已停` | 包还在到，但后端自报采集器已死 | **后端**的采集出了问题，不是网络 |
| `时钟异常` | 包里的时间戳不可信（在未来，或荒谬地旧） | 后端或代理的**系统时钟**，见下方「时钟不同步」 |
| `无数据` | 从来没收到过这个后端的包 | 后端没配 `network.enabled` / 后端一直空服 / 代理没装本插件 |

**首装失败时面板会自己给排查线索。** 只要没有任何一台后端处于「正常」，命令会在汇总行下面
追加一段三步排查提示（`network.enabled`、是否有玩家在线、代理是否已装本插件）。空服后端显示
「无数据」是**预期行为**，不是故障——这也是这段提示要说明的第一件事。

`采集已停` 这一行**整行都不显示数字**，哪怕包里带着 TPS——采集器死了以后那些数字是冻结的，
显示它们等于把历史当现状。这是本插件最核心的一条展示纪律。

`数据过期` 与 `时钟异常` 两行**保留数字但全部降为灰色**（`UNKNOWN`）：文字仍有信息
（「最后是 19.5」能帮服主判断停在哪一刻），但绿色会被读成「这台很健康」，而这两行的
结论恰恰不支持它。整行（六格）都不给健康色。

`时钟异常` 这一行的年龄格写的是「早 1小时（时间戳在未来）」或「落后 3天（时间戳在过去）」
这种正向表述，**不会**写「0 秒前」。时间戳不可信时，"数据是刚采的"这个结论本身就不可信，
写成 0 秒等于把伪造当事实。

### 数据年龄怎么读

「数据年龄」一列写的是**这块数据现在有多旧** = 距最后一次收到包的时间 + 包里那份快照
在到达时就已有的年龄。两者缺一不可：

- 只看「包里的年龄」不行——它锚定在包到达的那一刻（这是防伪造时间戳的设计），**不会随时间增长**。
  一台停摆一小时的后端，这个数仍停在刚到时的 0.3 秒，直接显示就是「0 秒前」。
- 只看「距最后一次收到多久」也不行——一个时间戳是十年前、但刚刚到达的包，前者接近 0，
  会被判成「正常」。

所以面板显示的是两者之和，三种状态都对：正常上报时它跟随上报节奏前进；后端停摆时它按停摆
时长增长；采集器死了而包还在到的时候，它也照样增长。


### 时钟不同步（v1.4.5-fix5 新增）

后端和代理是两台机器，时钟可能不同步。代理会从每个包的 `sentAt` 字段**学习**该后端的
时钟偏移（`sentAt - 到达时刻` 的滑动窗口取**最大值**，即 NTP 的 min-delay 滤波器），
再用它把年龄换算到对方的时间轴上。于是：

- **后端快 5 分钟**：不再"永远正常"。刚发的包显示正常，停摆后 30 秒照常变成「数据过期」。
- **后端慢 5 分钟**：不再"永远过期"。只要它在正常上报，就显示「正常」。
- **偏移超过 10 分钟**：不再参与学习——校正值封顶在 10 分钟，超出的部分不会被吸收。
  注意这**不等于**「超了就必然显示时钟异常」，两者的阈值不同：
- **伪造时间戳**：年龄锚定在"包到达的那一刻"，所以伪造最多换来刚到达时的一次"0 秒前"，
  30 秒后必然过期。修复前它可以换来**永久**「正常」。

**「时钟异常」这一档的真实判据**（两个方向，阈值不同）：

| 方向 | 阈值 | 常量 |
|---|---|---|
| 时间戳在**未来** | 超过 **60 秒** | `SummaryPacket.MAX_FUTURE_AHEAD_MS` |
| 时间戳在**过去** | 超过 **10 年** | `NetworkView.MAX_PLAUSIBLE_AGE_MS` |

为什么两侧差这么多：未来方向只要超过 60 秒就足以确定"这不是网络延迟能解释的"，
所以闸门开得紧；而过去方向不能紧——真实的数据可能因为后端刚重启而只有几秒旧，
也可能因为网络分区迟到几分钟，把闸门开到小时级会误伤。10 年这个数字的目的是
拦住"1969 年"这类**结构性错误**（把缺失的时间戳当成 0 用），不是为了衡量偏移。

两侧都判「时钟异常」而不是「数据过期」，因为文案要说准：没有任何空服会产出 1969 年的
时间戳，写成"可能空服"等于把人指向"没人玩"，而真正该看的是那台机器的时钟。

网络延迟按构造只会让年龄偏大（偏保守），不会被伪造成"更新鲜"。

### 阈值口径

TPS / MSPT 的分级阈值**硬编码在代理侧**（`NetworkRenderer`），取的是后端 `config.yml` 的
**随包默认值**：TPS 警告 18.0 / 严重 15.0，MSPT 警告 45.0 / 严重 50.0，且与后端一样用
**严格比较**（读数必须越过阈值才算越界，恰好等于不算）。

「严格」不是随手选的：后端所有与告警有关的判定都出自同一张算子表 `ThresholdOperator`，
其中 `tps` / `mspt` 是严格的（`tps < 15`、`mspt > 50`），只有内存与玩家占比是闭区间。
所以在这两个面板上都成立的一句话是「颜色变了就等于告警已经触发」——
恰好 15.00 的 TPS 两边都是黄，恰好 18.00 的两边都是绿。

代理侧读不到各后端的配置，所以如果你改了后端的 `tps.*` / `mspt.*` 阈值，两个面板的着色会不一致
——改了后端阈值就请同步改 `NetworkRenderer` 里的四个常量，或接受这个差异。

**不可信的读数写成「—」，而不是截到一个好看的数。** 摘要来自网络，坏包/伪造包可能发出
量级荒谬的值（`tps1m = 1e308`）。这类值不是一次测量，所以按"没有值"处理：

| 列 | 视为「—」的范围 | 为什么 |
|---|---|---|
| TPS | 负数、`NaN`、`> 1000` | 正常上限 20，`/tick sprint` 能到几百，1000 留足余量；`0` **是合法读数**（服务器冻结，必须照常判红） |
| MSPT | `≤ 0`、`> 60000` | `≤ 0` 是后端的"未采集"哨兵（与后端 `ThresholdColors` 同口径）；单 tick 卡住几秒是真实故障，必须显示 |

**这个校验做两次，因为出口有两个**：渲染层挡住它不能进那一格（否则一格 309 个字符会把整列、
进而**所有行**撑到 312 格），聚合层还要再挡一次（否则 `1e308` 会把"全网 TPS"污染成天文数字）。

### 表格宽度：一节专门说清楚

面板靠空格对齐，所以每一格都要按**显示宽度**填充。判据是：

1. **组合记号 / 格式符 → 0 格**（`é` 的声调、变体选择符、ZWJ、BOM、软连字符）
2. **East Asian Width 为 W / F → 2 格**（汉字、全角假名、韩文、全角标点、绝大多数 emoji）
3. **其余 → 1 格**（ASCII、半角假名 `ｱ`、以及 Ambiguous 一类）

emoji 按**字素簇**算：`👨‍👩‍👧‍👦`（4 个码点 + 3 个 ZWJ）在客户端里是**一个** 2 格字形，
不是 8 或 14 格。`👍🏽` 的肤色修饰同理。

**已知不精确，明确写在这里而不是假装没有：**

- **Ambiguous 类按 1 格**（`Ω`、`α`、`—`、`…`）。面板里实际会打印的只有 `—` 与 `…`，
  影响是"含这两个字符的格子最多偏 1 格"，不会累积到所有行。想按 2 格算会让纯拉丁/希腊文本
  被高估一倍，那个方向的错更常见。
- **keycap（`1️⃣`）**按 1 格，实际渲染 2 格。
- 完全精确需要一张 emoji 呈现序列表 + 逐字体 glyph 宽度表，两者都会随 Unicode 版本与资源包
  漂移。收益是几个像素，成本是一份长期要维护的表，所以不做。

**宽度有三道上限，防止一格撑爆整表：**

| 位置 | 上限 | 说明 |
|---|---|---|
| 后端名格 | 20 显示格 | 超出截断并加 `…`。真实后端名都在 16 格内 |
| 任意单列 | 32 显示格 | 总闸，保证整行不超过约 202 格 |
| `padTo` | 调用方给定宽度 | 超出**截断**（以前是原样返回，靠调用方顺序正确才不出错） |

> 为什么后端名要按**显示宽度**而不是 UTF-16 长度封顶：解析层那道闸门按字符数算（64），
> 管的是内存与单条消息尺寸；但 64 个汉字是 **128 显示格**，整行会被推到约 165 格，
> 在约 53 格的聊天框里折成三行。两个判据问的不是同一件事。

### 在线合计是"不完整"的时候

合计**只统计「正常」状态的后端**——把过期数字混进来等于编一个总数。但只给一个数字会被读成
"全服在线"，所以面板会同时写出**没计入多少**：

```
后端 4 个：正常 2 · 数据过期 1 · 无数据 1 ｜ 全网 TPS 15.00 ｜ 在线合计 15（+1 未计入）
```

读法：确认 15 人；另有 1 人的后端处于「数据过期」，它的数字不可信所以没算进来。

连读数都没有的后端会单列：`7（+3 未计入 · 另 1 台无读数）`——"有数但不信"与"连数都没有"
是两件事，混在一起会让人以为差额都是真实的人。

「无数据」**不算**"合计不完整"：这条链路走玩家连接，从没上报的后端几乎必然是空服。
若把它也算进缺失，每个有若干空服后端的网络都会永远带着这个标记，标记就此贬值。

### 过期判定跟随后端的上报间隔

包里有 `pushIntervalSec` 字段（后端 `network.push-interval-seconds` 原值）。代理按
`3 × 该值` 判"数据过期"，所以服主把间隔调大到 60 秒也没问题；只有旧版后端发的包不带这个字段时，
才回退到代理自己的 10 秒假设（3 × 10 = 30 秒）。

## 后端侧要配什么

在各 Paper 后端的 `config.yml`：

```yaml
network:
  enabled: true
  server-id: "survival"       # 每个后端必须不同，否则代理侧会把它们混成一条
  push-interval-seconds: 10
```

**`server-id` 有三条硬限制，代理与后端两端同时校验（判据逐字一致）：**

| 限制 | 值 | 超限后果 |
|---|---|---|
| 长度 | ≤ **64** 个字符（按字符数，不按字节；中文一字算 1） | 后端**拒发**并告警；代理对越界包整包丢弃 |
| 保留字 | 不能是 **`unknown`**（大小写敏感，`Unknown` 合法） | 同上 |
| 字符 | 不能含控制符（C0 0x00–0x1F、C1 0x80–0x9F、DEL 0x7F）或 **`§`**（U+00A7） | 后端**拒发**并点出是哪个码点；代理对收到的包**剔除**这些字符后继续用 |

后端在**发送前**就拦住，日志点名"长度 / 保留字 / 含非法字符"并给出实际字符数与上限——这正是为了修掉
早年的失败形态：超长 id 被代理静默丢弃，代理日志只说"无法解析的跨服摘要，请检查版本"，
把服主引向一个完全无关的方向（两端版本不一致），照着查会彻底查错。

> 为什么控制符也要在后端拦：代理侧会把它们**剔除**，于是 `survival\u0007` 与真正的 `survival`
> 会塌成同一个 id——先上报的那一方抢注成功，真正的后端随后被判成冒充而**永久丢包**。

> 长度上限 64 是**协议常量**，不是可调项。两端不能共享代码（一个 Paper 一个 Velocity），
> 所以靠"同一个字面量 64"对接，两侧测试各钉一遍。

### 摘要里的控制字符会被剔除

`server` 字段来自网络，会被原样拼进管理员聊天窗口的一行表格。所以代理侧读出来后**剔除**
控制字符（`\n` `\r` `\t`、C0/C1 控制符、DEL）与 `§`（U+00A7，legacy 格式码前缀）：

- `\n` / `\r` 会把面板行劈成两行——那是纯粹的视觉伪造，管理员会把不存在的服务器当成真的；
- `\t` 会打乱列对齐；BEL / ESC 会在终端日志里触发响铃 / 转义序列；
- `§c` 之类在任何 legacy 序列化场合就是颜色码，能让一台后端把面板染色、把相邻列吃掉。

剔除而不是整包拒收：拒收会让那台后端隐身（与超长 id 同一个失败形态），而它的数字可能是好的。

**强烈建议 `server-id` 与 `velocity.toml` 里该后端的名字逐字一致**（不是强制，理由见下）。代理面板的行集合是
「`[servers]` 里注册的名字」∪「收到过包的 `server-id`」，两者对不上就会出现**幽灵行**：

```yaml
# velocity.toml
[servers]
survival-1 = "10.0.0.11:25565"
skyblock-1 = "10.0.0.12:25565"
lobby      = "10.0.0.13:25565"
```

```yaml
# survival-1 那台的 config.yml
network:
  enabled: true
  server-id: "survival-1"     # 建议与上面的名字逐字一致（大小写也算）
```

若填成 `survival`，面板上会同时出现 `survival-1`（无数据）与 `survival`（有数）两行。

### 来源绑定：为什么"不一致"不拒绝，但"抢占"必须拒

区块 `server` 字段是后端自己填的，所以只判"消息来自某个后端连接"挡不住 **A 后端冒充 B**——
一台被植入插件的后端可以用 `server="B"` 把 B 的数据整个覆盖掉（染红 B，或把真正在卡的 B
伪装成 20 TPS 让告警永不响）。代理侧因此做**来源绑定**：`ServerConnection.getServerInfo().getName()`
（即 `velocity.toml` 的 `[servers]` 键，后端伪造不了）在收到第一个包时把每个 `server-id`
钉到一条后端上。

判据刻意**不要求名字相等**，只要求"一个身份只归一条后端"：

| 情形 | 处理 | 为什么 |
|---|---|---|
| 某 `server-id` 第一次出现 | 绑定到当时那条后端 | — |
| 之后同一 `server-id` 从**同一条**后端来 | 正常收数 | 无论名字是否等同于 `velocity.toml` |
| 之后同一 `server-id` 从**另一条**后端来 | **丢弃**并告警 | 这就是 A 覆盖 B 的形状 |

**为什么不强制 `server-id` 等于后端名。** README 早年写过"必须一致"，但那只是**建议**，
现有部署里一定有人没照做（把 `server-id` 当对外展示的友好名，与内部注册名分开）。如果
强制一致或"不一致就丢"，这些部署升级后会**一夜之间全部隐身**，症状（面板全空）与"代理没装
插件"一模一样，极难自查。而"一个身份只归一条后端"这个更弱的判据已经**堵住了覆盖攻击**：
A 想冒充 B，要么用 B 的 id（被 B 先占着 → 丢），要么用 A 自己的 id（覆盖的是 A 自己，无害）。

名字不一致时仍会**告警**（每对 id/后端一次），因为那是幽灵行的唯一线索——
但只在确实不一致时报，正常部署安安静静。

**`/pscope network reset` 会一并清空绑定表**：换过后端、或改了 `server-id` 之后，旧的
"某 id 归某后端"若留着，新后端会被判成抢占而永久丢包。

还要保证各后端装了 PerfScope 并在它们的 `config.yml` 里开了 `network.enabled`。

**关于代理的转发模式**：`modern` 与 `traditional` / `legacy` **都能用**。
此前本文档写过"modern 下 plugin messaging 不可用"，那是**错的**——modern 转发本身就是靠
`velocity:player_info` 这条 plugin message 完成握手的；后端→代理的 plugin message 路径
（`BackendPlaySessionHandler`）里没有任何转发模式分支，唯一的门控是"这个通道有没有被注册"。
真正在 modern 下不可用的是 BungeeCord 那条 legacy 专用通道，与本插件无关。
**不要为了这个问题把代理降级成 legacy**——那会引入比它更糟的信任模型。

### 它看不到什么

面板只有四个指标：**TPS(1m) / MSPT / 在线玩家数 / 采集是否活着**。实体数、区块数、内存、
CPU、热点区块这些仍然要登到那台后端上用 `/perfscope` 看——代理侧没有 tick 循环，也没有世界，
本来就没有可采的东西，摘要因此刻意做得很小（每台每轮几十字节）。

## 两个仓库的关系

| 仓库 | 装在哪 | 作用 |
|---|---|---|
| [Minecraft-server-plugin-PerfScope](https://github.com/sqkl520/Minecraft-server-plugin-PerfScope) | 每个 Paper 后端 | 采集指标 + 发送摘要 |
| 本仓库 | Velocity 代理 | 接收摘要 + 渲染 `/pscope network` |

**版本兼容规则**：`SummaryPacket.PROTOCOL_VERSION` 决定能不能通信。
规则是**单向的**——接收方接受「协议版本 ≤ 本端」的包，丢弃「高于本端」的包
（`version < 1 || version > PROTOCOL_VERSION` 即拒）。所以两侧**不必完全相同**，
但代理侧的协议版本**不能低于**后端：后端的号一旦更高，包会被代理整包丢弃。
artifact 版本（`1.4.5-SNAPSHOT-fix4` 这种）只决定"这是哪一版代码"，两者不要混。
协议版本不一致时，高版本发的包会被低版本**直接丢弃并记日志**（每分钟最多一条，附带丢弃条数
与**对方声明的版本**，便于判断该升哪一侧），而不是"尽力解析"——
后者会把新字段读成缺失，正是本项目反复修的那类静默失真。

**升级顺序**：先升代理侧，再升后端。因为接收方只拒「高于本端」的包，代理侧协议版本
≥ 后端版本时最平稳；反过来（后端先升到更高协议）会有一段时间全被丢弃。同一协议版本内
前后端可以任意顺序升级。

## 清空面板：`reset`

```
/pscope network reset
```

清空已收到的全部数据，让面板从头开始统计。换后端、调完 `server-id`、或者排查时想让
「幽灵行」消失，都可以用一次；下次收到包之前面板是空的（真「无数据」，不是上次的残影）。
权限同 `/pscope network`（`perfscope.network`），别名写法同样接受
`/perfscope network reset`、`/ps network reset`。

## 构建

```bash
mvn clean package
node tools/check-velocity-descriptor.mjs   # 校验 jar 里的描述符
```

产物：`target/PerfScope-Velocity-<version>.jar`，丢进 Velocity 的 `plugins/` 目录。

`mvn clean package` 会先跑单元测试，再把 Gson shade 进 jar（落点
`cn.perfscope.velocity.shaded.gson`）；Velocity API 本身是 `provided`，绝不打进 jar。常用变体：

```bash
mvn test                         # 只跑测试
mvn test -Dtest=SummaryTest      # 跑单个测试类
mvn clean package -DskipTests    # 跳过测试打包
```

## 那个 `resources-filtered` 目录是干什么的

Velocity 的注解处理器在**编译期**生成 `velocity-plugin.json`，它把 `@Plugin` 注解里的 version
字符串原样写进去，**不经过 Maven 的 resource filtering**。所以第一次打包出来的描述符里是字面量
`"version": "${project.version}"`。

这不是无害的：Velocity 会把它作为插件版本显示在 `/velocity plugins` 里，排错时核对版本也读它。
更糟的是它不报错——插件照常加载，只是版本那一栏永远是个占位符。

`src/main/resources-filtered/velocity-plugin.json` 是一份带 `${project.version}` 的模板，
由 `maven-resources-plugin` 在 `process-classes` 阶段（晚于 compile、早于 package）覆盖处理器
写出的那一份。`tools/check-velocity-descriptor.mjs` 负责防止它再次退化。

## 测试

用例全部打在纯逻辑层（`SummaryPacket` / `NetworkView` / `NetworkRenderer`）——
这三个类刻意不 import `com.velocitypowered.*`，因为 Velocity 的 API 在单测里没法实例化，
而判定与渲染才是真正会出错的部分。

（要当下准确的数目，读 `mvn test` 的 surefire 汇总那行 `Tests run: …`，不要数源码里的
`@Test`——条件跳过的用例在源码里仍是一条 `@Test`，两者会差几个。历史上本页曾写死
「18 个用例」，而提交树里实际早已是 36 个；为了避免再出现这种漂移，这里不再钉一个会过期的常数。）

采集已死仍显示数字——四条全部 KILLED。
